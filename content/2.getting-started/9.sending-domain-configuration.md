Postal separates the **Postal installation** from the **domains that Postal sends mail for**.

For example:

```text
Postal installation:
    postal.example.com

Sending domains:
    example.com
    transactional.example.com
    customer-example.com
```

A sending domain is the domain used in the visible `From:` address of messages sent through Postal.

::callout{icon="i-heroicons-information-circle"}
The Postal hostname does not have to be the sending domain. This guide uses `postal.example.com` as the canonical documentation example; a deployment may use another stable hostname, such as `mail.example.com`. The hostname is independent from `dkim_identifier`, `domain_verify_prefix`, and `custom_return_path_prefix`. Do not infer DNS prefixes or sending-domain records from the Postal hostname.
::

## Organization and Mail Server

In the Postal Web UI, create an Organization and then one or more Mail Servers within it.

A simple deployment may look like:

```text
My Company
└── Transactional
    └── example.com
```

Postal domains can be owned by an Organization or directly by a Mail Server. A Mail Server can authenticate and send using a verified domain associated with that server or with its Organization.

::callout{icon="i-heroicons-information-circle"}
Choose one ownership model for each domain based on how it should be shared. Avoid creating duplicate domain objects at both Organization and Mail Server level unless that is intentional.
::

## Add the sending domain

Add the exact domain that you intend to use in the `From:` address.

For example:

```text
example.com
```

or:

```text
transactional.example.com
```

A parent domain and a sending subdomain are separate Postal domains and are verified independently.


## Email address roles: `From` and `MAIL FROM`

Before configuring SPF, DKIM and DMARC, it is important to distinguish the visible sender from the SMTP envelope sender.

The message `From:` header is the address shown to the recipient and is the identity used for DMARC alignment. The SMTP `MAIL FROM` address is part of the delivery envelope and is used for SPF evaluation and bounce handling. The two addresses may use different domains.

The SMTP `HELO`/`EHLO` name is a third SMTP identity. It identifies the sending host during the SMTP session and is separate from both the visible `From:` address and the envelope `MAIL FROM` domain. See the dedicated HELO/EHLO section below for the required production DNS relationship.

For example:

```text
From:     hello@example.com
MAIL FROM: bounces@psrp.example.com
```

This is a normal Postal-style arrangement when a Return Path subdomain is used. The envelope address is not normally displayed by the mail client.

::callout{icon="i-heroicons-information-circle"}
**DMARC alignment matters:** SPF authenticates the `MAIL FROM` domain, while DKIM authenticates the domain in the `d=` value. DMARC checks whether at least one authenticated identifier is aligned with the domain in the `From:` header.
::

## HELO/EHLO hostname

The `dns.helo_hostname` setting controls the hostname Postal presents in the `HELO` or `EHLO` command when it connects to remote SMTP servers for outbound delivery.

For a standard production deployment, use the same public fully qualified domain name (FQDN) for `dns.helo_hostname` and `postal.smtp_hostname`:

```yaml
postal:
  smtp_hostname: postal.example.com

dns:
  helo_hostname: postal.example.com
```

This keeps the Postal SMTP hostname and the SMTP session identity aligned:

```text
SMTP hostname:  postal.example.com
HELO/EHLO:      postal.example.com
```

Postal treats these settings as separate values. A different `dns.helo_hostname` can intentionally override `postal.smtp_hostname`, and leaving `dns.helo_hostname` empty allows Postal to use its normal fallback behavior. Matching the two values is therefore a **recommended production configuration**, not a hard schema requirement.

::callout{icon="i-heroicons-information-circle"}
**Keep `postal.smtp_hostname` and `dns.helo_hostname` identical unless you have a documented reason to use a separate outbound SMTP identity.** Changing them independently makes DNS, TLS certificates, reverse DNS, and SMTP diagnostics harder to reason about.
::

### Forward DNS, reverse DNS (PTR/rDNS), and FCrDNS

The HELO/EHLO hostname should be a real public FQDN and should be consistent with the public IP address used for outbound SMTP connections. Three related DNS concepts matter here:

- **Forward DNS:** the hostname resolves to the sending IP address through an `A` and/or `AAAA` record.
- **Reverse DNS (rDNS/PTR):** the sending IP address has a `PTR` record that returns the SMTP hostname.
- **FCrDNS (Forward-Confirmed Reverse DNS):** the hostname returned by the `PTR` record resolves forward to the same IP address.

For example:

```text
203.0.113.10
    PTR → postal.example.com

postal.example.com
    A → 203.0.113.10
```

With IPv6, the same consistency should exist for the address used for SMTP connections:

```text
2001:db8::10
    PTR → postal.example.com

postal.example.com
    AAAA → 2001:db8::10
```

The resulting identity chain should be:

```text
Outbound SMTP IP
       │
       ▼
    PTR/rDNS
       │
       ▼
HELO/EHLO hostname
       │
       ▼
   A / AAAA
       │
       ▼
same SMTP IP
```

This is the practical meaning of FCrDNS: the reverse and forward DNS mappings confirm each other. FCrDNS is not a separate DNS record and does not have a Postal-specific configuration switch.

::callout{icon="i-heroicons-check-circle"}
**Recommended production state:** the outbound SMTP IP has a `PTR` record pointing to the hostname used in `HELO`/`EHLO`, and that hostname has matching `A`/`AAAA` records pointing back to the same outbound IP.
::

### TLS certificate and SMTP identity

When SMTP TLS is enabled, the certificate presented by the SMTP service should contain the hostname that remote systems use as the SMTP endpoint. Keeping `postal.smtp_hostname` and `dns.helo_hostname` aligned with the public SMTP certificate name reduces hostname mismatch problems during TLS negotiation.

If a separate `helo_hostname` is intentionally used, configure and verify the associated DNS and certificate identity as part of the same deployment rather than treating it as an independent cosmetic value.

::callout{icon="i-heroicons-exclamation-triangle"}
**Do not use `localhost`, a container hostname, an internal-only name, or an unresolvable hostname for outbound HELO/EHLO.** The value is presented to external SMTP servers and should identify the public sending system.
::

### When can the values differ?

A different `dns.helo_hostname` is appropriate only when you intentionally operate a separate outbound SMTP identity. For example:

```yaml
postal:
  smtp_hostname: mail.example.com

dns:
  helo_hostname: outbound.example.com
```

In that configuration, `outbound.example.com` becomes the identity used in the SMTP `HELO`/`EHLO` command. Its forward DNS, reverse DNS, TLS certificate, and outbound source IP should be configured consistently.

::callout{icon="i-heroicons-information-circle"}
**Advanced configuration:** a different HELO hostname is supported, but it should be deliberate. Do not change only the HELO value while leaving the corresponding DNS or certificate identity unchanged.
::

### Operational verification

Before production, verify the complete forward/reverse chain:

```bash
dig A postal.example.com
dig AAAA postal.example.com
dig -x 203.0.113.10
```

The forward lookup should contain the public outbound SMTP IP and the reverse lookup should return the hostname Postal presents in `HELO`/`EHLO`.

For a single IPv4 address, the expected relationship is:

```text
HELO/EHLO:   postal.example.com
PTR/rDNS:    203.0.113.10 → postal.example.com
Forward DNS: postal.example.com → 203.0.113.10
```

## Domain verification

Postal supports DNS-based and email-based domain verification. DNS verification is generally easier to automate and is the method described here.

With the default configuration:

```yaml
dns:
  domain_verify_prefix: postal-verification
```

Postal constructs a verification TXT value in the form:

```text
postal-verification <TOKEN>
```

If the domain is `example.com`, publish:

```dns
example.com.    TXT    "postal-verification <TOKEN>"
```

If you customize the prefix, for example:

```yaml
dns:
  domain_verify_prefix: dkim-verification
```

the value becomes:

```dns
example.com.    TXT    "dkim-verification <TOKEN>"
```

::callout{icon="i-heroicons-exclamation-triangle"}
`domain_verify_prefix` is part of the TXT **value**, not a DNS hostname. Do not create `postal-verification.example.com` or `dkim-verification.example.com` for this check.
::

Postal looks up TXT records for the exact domain configured in Postal and searches for the generated verification string.

## SPF

The sending domain must publish an SPF record containing the Postal SPF include configured in `dns.spf_include`.

For example:

```dns
example.com.    TXT    "v=spf1 include:spf.postal.example.com -all"
```

If another provider already sends mail for the domain, combine the providers in a single SPF policy rather than publishing multiple independent SPF records:

```dns
example.com.    TXT    "v=spf1 include:_spf.example-provider.com include:spf.postal.example.com -all"
```

::callout{icon="i-heroicons-exclamation-triangle"}
Use one SPF policy record for the domain. Keep the complete SPF evaluation chain within the SPF DNS lookup limit. Use `-all` for the hardened production policy only after all legitimate senders are included.
::

### Migration mode

During a migration or initial validation, the policy can temporarily use:

```text
~all
```

This is a soft-fail policy.

After all legitimate senders have been verified, use:

```text
-all
```

for the final hardened policy.

Keep the SPF evaluation chain below the DNS lookup limit. Avoid unnecessary nested `include` chains and deprecated mechanisms such as `ptr`.

Postal's DNS checker requires a valid SPF record containing the configured `spf_include`; it does not require either `~all` or `-all` specifically.

## DKIM

Postal generates a unique DKIM selector for each domain.

With:

```yaml
dns:
  dkim_identifier: postal
```

an example selector may be:

```text
postal-ABCDEF
```

and the corresponding record name:

```text
postal-ABCDEF._domainkey.example.com
```

If you configure:

```yaml
dns:
  dkim_identifier: dkim
```

the selector instead uses the `dkim` prefix, for example:

```text
dkim-ABCDEF._domainkey.example.com
```

Use the exact selector and TXT value generated by Postal for the domain. For a sending domain, use the domain-specific DKIM record shown/generated for that domain; do not use the output of `postal default-dkim-record` for the sending domain.

::callout{icon="i-heroicons-exclamation-triangle"}
Do not replace Postal's generated selector with a generic `dkim._domainkey.example.com` record. The selector contains a per-domain identifier.
::

Postal includes `t=s` in the DKIM record it generates, which limits that key to the exact domain at which the record is published.

The current Postal source generates 1024-bit RSA DKIM keys. This is an implementation detail of the current application and should be considered when evaluating cryptographic requirements.

::callout{icon="i-heroicons-information-circle"}
**Ed25519 note:** the current Postal implementation generates RSA DKIM keys. Do not publish an Ed25519 DKIM record and expect Postal to sign with it; Ed25519 would require a different signing implementation or an external signing layer.
::

### DKIM signing behavior

Postal uses the domain-specific DKIM key when the domain's stored DKIM status is `OK`. If the domain is not in that state, the current signing code falls back to the global Postal signing key and the configured `return_path_domain`.

::callout{icon="i-heroicons-exclamation-triangle"}
For production traffic, verify that Postal reports the expected DKIM DNS record as `OK`. A domain that has not passed the DKIM check may be signed with Postal's fallback identity instead of the sending domain's DKIM identity.
::

There is no DKIM equivalent of SPF's `~all` or `-all`. DKIM verification either succeeds or fails; DMARC determines how an aligned authentication failure is handled.

::callout{icon="i-heroicons-information-circle"}
For key rotation, publish a new selector and key before removing the old selector. Keep the old key available long enough for previously sent messages to age out of receiving systems' caches. Do not overwrite an active selector in place unless you are deliberately managing that transition.
::

## Return Path

Postal derives a Return Path hostname from the sending domain and `dns.custom_return_path_prefix`.

With:

```yaml
dns:
  custom_return_path_prefix: psrp
  return_path_domain: rp.postal.example.com
```

and the sending domain:

```text
example.com
```

Postal derives:

```text
psrp.example.com
```

Create:

```dns
psrp.example.com.    CNAME    rp.postal.example.com.
```

For:

```text
transactional.example.com
```

the derived hostname becomes:

```text
psrp.transactional.example.com
```

::callout{icon="i-heroicons-exclamation-triangle"}
Do not move a derived Return Path record to the parent domain. The hostname is constructed from the exact sending-domain name.
::

## DMARC

### Production policy

For a hardened production configuration, use `p=reject` after all legitimate senders have been verified. During migration, `p=none` provides monitoring without enforcement and `p=quarantine` requests that failing messages be treated as suspicious. These are migration stages, not equivalent final policies.

DMARC is configured in DNS. There is no Postal `postal.yml` setting for the DMARC policy.

For a hardened production policy, publish a DMARC record for the sending domain:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; pct=100; rua=mailto:dmarc@example.com"
```

The important policy tags are:

- `p=reject` requests rejection of messages that fail DMARC for the policy domain.
- `sp=reject` applies the reject policy to subdomains that do not publish their own DMARC policy.
- `adkim=s` uses strict DKIM identifier alignment.
- `aspf=r` uses relaxed SPF identifier alignment.
- `pct=100` applies the requested policy to 100% of applicable messages.
- `rua` requests aggregate DMARC reports.

::callout{icon="i-heroicons-information-circle"}
If the `rua` address belongs to a different organizational domain, that reporting domain must explicitly authorize reports for the sending domain. Using a mailbox such as `dmarc@example.com` keeps this setup simpler.
::

::callout{icon="i-heroicons-information-circle"}
`aspf=r` is deliberate for Postal's standard Return Path design. A message using `From: user@example.com` may use an envelope return-path subdomain such as `psrp.example.com`. Relaxed SPF alignment allows those identifiers to align at the organizational-domain level. Strict SPF alignment can fail when the domains differ by subdomain.
::

When Postal has a working domain-specific DKIM record, the DKIM signing domain is the sending domain, so strict DKIM alignment can be used with `adkim=s`.

### DMARC migration modes

A new domain can initially be monitored with:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=none; sp=none; adkim=s; aspf=r; pct=100; rua=mailto:dmarc@example.com"
```

An intermediate enforcement policy can use:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=quarantine; sp=quarantine; adkim=s; aspf=r; pct=100; rua=mailto:dmarc@example.com"
```

The final hardened policy is:

```dns
_dmarc.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; pct=100; rua=mailto:dmarc@example.com"
```

::callout{icon="i-heroicons-information-circle"}
`p=none` and `p=quarantine` are useful migration stages. They are not equivalent to the final `p=reject` enforcement policy. Review aggregate reports before moving a production domain to rejection.
::


## Additional email hardening

The DNS records above provide the authentication required for a Postal sending domain. The following measures are optional and depend on whether the domain is used for receiving mail, branding, or both.

### MTA-STS for inbound mail

MTA-STS protects **inbound** SMTP delivery to a domain by allowing sending MTAs to require TLS and to verify that the MX hostname is one of the hosts permitted by the domain's policy. It is relevant only when the domain actually receives mail.

For example, if:

```text
example.com. MX 10 postal.example.com.
```

an MTA-STS policy can be published at:

```text
https://mta-sts.example.com/.well-known/mta-sts.txt
```

and the policy can contain:

```text
version: STSv1
mode: enforce
mx: postal.example.com
max_age: 604800
```

The policy host requires a valid HTTPS certificate, and the `mx:` entries must match the TLS-capable MX hosts used by the domain. The receiving SMTP service must also support STARTTLS before an MTA-STS policy is enforced. The policy file is retrieved over HTTPS from the `mta-sts` host; it is not stored in DNS.

The corresponding discovery record is published at `_mta-sts.example.com`. For example:

```dns
_mta-sts.example.com.    TXT    "v=STSv1; id=2026091801"
```

The `id` value is an opaque policy version identifier. Change it whenever the policy changes so that supporting senders can refresh their cached policy.

For staged deployment, MTA-STS also defines `mode: testing`. Use `testing` while validating policy coverage and TLS behavior, then move to `enforce` when all intended MX hosts are ready. `mode: none` disables MTA-STS enforcement for the domain. The policy must contain one or more `mx:` entries when `mode` is `testing` or `enforce`.

::callout{icon="i-heroicons-information-circle"}
For a single-node Postal deployment, `postal.example.com` may be the only MX listed in both DNS and the MTA-STS policy. For a multi-node deployment, list each permitted MX hostname separately. MTA-STS does not configure Postal; it is a domain-level receiving policy.
::

### SMTP TLS Reporting (TLS-RPT)

SMTP TLS Reporting (TLS-RPT) is a **reporting mechanism**, not a TLS enforcement policy. It tells a sending mail system where to submit aggregate reports about TLS delivery problems encountered when connecting to a receiving domain. It is therefore most useful alongside MTA-STS or DANE, which provide the actual transport-security policy.

TLS-RPT is configured in DNS for the **receiving domain**. It is not a Postal `postal.yml` setting and it does not control how Postal sends mail to unrelated recipient domains.

For `example.com`, publish exactly one effective TLS-RPT policy at:

```dns
_smtp._tls.example.com.    TXT    "v=TLSRPTv1; rua=mailto:tlsrpt@example.com"
```

The format is deliberately small. TLS-RPT v1 defines these policy fields:

| Field | Required | Description |
| --- | --- | --- |
| `v` | **Yes** | Must be exactly `TLSRPTv1` and appears first in the record. |
| `rua` | **Yes** | One or more report destination URIs. `mailto:` and `https:` are the supported URI schemes. |

A policy may use more than one report destination:

```dns
_smtp._tls.example.com.    TXT    "v=TLSRPTv1; rua=mailto:tlsrpt@example.com, https://reports.example.com/tls"
```

Whitespace around semicolons and commas is allowed. URI delimiters such as commas, exclamation marks, and semicolons that are part of a URI must be percent-encoded rather than interpreted as TLS-RPT syntax.

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
**Publish one effective TLS-RPT policy.** If DNS returns multiple `v=TLSRPTv1` records for `_smtp._tls.<domain>`, senders must treat the domain as not implementing TLS-RPT. Records that do not begin with `v=TLSRPTv1;` are ignored when determining the effective set.
::

### TLS-RPT DNS record details

A single DNS TXT record may be split into several quoted character strings by the DNS provider, for example:

```dns
_smtp._tls.example.com. TXT (
    "v=TLSRPTv1; "
    "rua=mailto:tlsrpt@example.com"
)
```

Those strings are concatenated without an inserted space before TLS-RPT parsing. Keep separators inside the text exactly where they are required.

TLS-RPT v1 parsers are required to accept syntactically valid extension fields. Unknown extension fields are ignored by implementations that support a compatible superset of the specification. Do not depend on private fields for interoperability.

Unlike DMARC, TLS-RPT does **not** define a separate DNS authorization record for third-party reporting destinations. The `rua` URI can point to another domain; the report receiver is responsible for protecting and operating that endpoint correctly.

::callout{icon="i-heroicons-information-circle"}
For security and operational reliability, use an HTTPS report endpoint with a valid certificate or a dedicated mailbox that can accept automated aggregate reports. Avoid routing TLS-RPT reports into the same infrastructure whose TLS failures you are trying to diagnose.
::

### TLS-RPT report transports

#### `mailto:`

When `rua` contains a `mailto:` URI, the report is delivered as an email message. A machine-readable report uses `multipart/report` with `report-type="tlsrpt"`; the machine-readable part is `application/tlsrpt+json` or, when compressed, `application/tlsrpt+gzip`.

TLS-RPT email reports use these headers:

```text
TLS-Report-Domain: example.com
TLS-Report-Submitter: sender.example.net
```

The report body is I-JSON. Compression with gzip is recommended because aggregate reports can become large.

#### `https:`

When `rua` contains an `https:` URI, the report is submitted to that endpoint with an HTTP `POST` request. The endpoint should accept the TLS-RPT media type and return a successful HTTP response when the report has been accepted.

A TLS-RPT implementation may support multiple `rua` destinations. If one destination is unavailable, an implementation may try another supported destination. Delivery should not be considered complete until at least one configured destination has accepted the report.

### TLS-RPT report format

TLS-RPT reports are aggregate JSON documents. A report contains:

```json
{
  "organization-name": "Example Organization",
  "date-range": {
    "start-datetime": "2026-09-18T00:00:00Z",
    "end-datetime": "2026-09-19T00:00:00Z"
  },
  "contact-info": "mailto:tlsrpt@example.com",
  "report-id": "example-20260918-001",
  "policies": [
    {
      "policy": {
        "policy-type": "sts",
        "policy-string": "version: STSv1; mode: enforce; mx: postal.example.com",
        "policy-domain": "example.com",
        "mx-host": "postal.example.com"
      },
      "summary": {
        "total-successful-session-count": 1200,
        "total-failure-session-count": 3
      },
      "failure-details": []
    }
  ]
}
```

The main fields are:

| Field | Description |
| --- | --- |
| `organization-name` | Organization responsible for the report. |
| `date-range` | UTC start and end timestamps covered by the report. |
| `contact-info` | Contact information for the report submitter. |
| `report-id` | Unique report identifier. |
| `policies` | Array of policy observations and their session counts. |
| `policy.policy-type` | `sts`, `tlsa`, or `no-policy-found`. |
| `policy.policy-string` | The applicable MTA-STS policy or DANE TLSA data, or the literal `no-policy-found`. |
| `policy.policy-domain` | Domain for which the policy was evaluated. |
| `policy.mx-host` | MX hostname or policy MX pattern involved. |
| `summary.total-successful-session-count` | Number of successful TLS sessions. |
| `summary.total-failure-session-count` | Number of failed TLS sessions. |
| `failure-details` | Array describing the observed failure categories. |

A failure detail can include `result-type`, `sending-mta-ip`, `receiving-mx-hostname`, `receiving-mx-helo`, `receiving-ip`, `failed-session-count`, `additional-information`, and `failure-reason-code`.

The standardized result categories include:

| Result type | Meaning |
| --- | --- |
| `starttls-not-supported` | The receiving SMTP server did not offer STARTTLS. |
| `certificate-host-mismatch` | The presented certificate did not match the expected SMTP hostname. |
| `certificate-expired` | The certificate was expired. |
| `certificate-not-trusted` | The certificate could not be validated against the expected trust model. |
| `validation-failure` | A TLS validation failure that does not fit another defined category. |
| `tlsa-invalid` | The DANE TLSA data could not be used successfully. |
| `dnssec-invalid` | DNSSEC validation failed. |
| `dane-required` | DANE was required but could not be successfully used. |
| `sts-policy-fetch-error` | The MTA-STS policy could not be retrieved. |
| `sts-policy-invalid` | The retrieved MTA-STS policy was invalid. |
| `sts-webpki-invalid` | The HTTPS MTA-STS policy could not be authenticated with normal Web PKI validation. |

A single failed session may be represented by more than one failure detail when several independent checks fail. Transient failures such as a busy network or a TCP timeout are not required to be reported.

### TLS-RPT reporting interval, compression, and retries

Reports normally cover a daily UTC reporting period. The reporting implementation may delay report submission to avoid synchronized bursts of traffic.

Gzip compression is recommended for both email and HTTPS delivery. Compressed reports use:

```text
application/tlsrpt+gzip
```

Uncompressed reports use:

```text
application/tlsrpt+json
```

A failed report delivery should be retried for up to 24 hours using an appropriate backoff strategy. The reporting system should tolerate delayed or duplicated reports by using the report ID as a stable identifier.

### TLS-RPT and MTA-STS/DANE

TLS-RPT does not enforce encrypted SMTP on its own.

```text
TLS-RPT
    = reporting

MTA-STS
    = policy and certificate/hostname enforcement through HTTPS policy

DANE
    = DNSSEC-backed TLSA policy
```

For a domain protected by MTA-STS or DANE, TLS-RPT provides visibility into policy and TLS failures seen by sending MTAs.

::callout{icon="i-heroicons-information-circle"}
Publishing `_smtp._tls.example.com` affects MTAs delivering **to** `example.com`. It does not create a global TLS policy for mail sent by Postal. When Postal delivers to a recipient domain, Postal is the sender and the recipient domain's TLS policies apply.
::

When TLS-RPT reports are themselves delivered by SMTP, an implementation must not allow an MTA-STS or DANE TLSA failure for the report's delivery to prevent the reporting mechanism from functioning. This exception exists so that transport-security failures can still be reported.

### TLS-RPT operational checklist

```text
[ ] Publish exactly one effective _smtp._tls TXT record.
[ ] Use v=TLSRPTv1 as the first field.
[ ] Configure at least one valid mailto: or https: rua destination.
[ ] Make sure the report destination can accept aggregate reports.
[ ] Prefer gzip compression for large reports.
[ ] Monitor failure categories instead of treating any single transient failure as proof of an outage.
[ ] Use TLS-RPT together with MTA-STS or DANE when transport enforcement is required.
[ ] Keep the reporting endpoint independent from the SMTP service being monitored.
```

### DANE for SMTP

DANE can provide certificate pinning and TLS enforcement for **inbound** SMTP, but it requires DNSSEC. It is an advanced option and requires careful certificate/key rotation because the corresponding TLSA record must remain synchronized with the SMTP service certificate or public key.

For an SMTP service at `postal.example.com` on TCP port 25, a TLSA record is published at:

```dns
_25._tcp.postal.example.com.    TLSA    3 1 1 <SHA256_SPKI_DIGEST>
```

The example uses certificate usage `3` (DANE-EE), selector `1` (subject public key info), and matching type `1` (SHA-256). Generate the digest from the public key material used by the SMTP certificate; do not copy the placeholder.

Do not enable DANE solely by adding a TLSA record. The domain's DNSSEC chain must validate, the SMTP service must support TLS, the SMTP certificate must match the TLSA record, and your MX host must be stable enough to support the operational requirements of DANE.

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
A stale TLSA record can make mail delivery fail. Treat certificate renewal, key rotation, DNSSEC maintenance, and TLSA updates as one change set.
::

### BIMI

BIMI is an optional branding mechanism for participating mailbox providers. It does not improve Postal's SMTP delivery logic and is not configured through `postal.yml`.

A typical record uses the `default` selector:

```dns
default._bimi.example.com.    TXT    "v=BIMI1; l=https://example.com/logo.svg; a=https://example.com/bimi_cert.pem"
```

The SVG logo and certificate must be served over HTTPS. BIMI-capable mailbox providers may apply additional requirements, and a strong DMARC policy is required for BIMI deployment in practice. Use `p=quarantine` or `p=reject` with a fully covered policy before expecting BIMI to be displayed consistently.

::callout{icon="i-heroicons-information-circle"}
Postal does not generate or validate BIMI records. Treat BIMI as an optional DNS/brand configuration on the sending domain.
::

### Hardening unused domains and subdomains

A domain that is not supposed to send mail should still be protected against spoofing.

For a domain with **no legitimate outbound mail**, publish:

```dns
example.net.    TXT    "v=spf1 -all"
_dmarc.example.net.    TXT    "v=DMARC1; p=reject; sp=reject; pct=100"
```

If the domain also does not accept inbound mail, publish a null MX:

```dns
example.net.    MX    0 .
```

A null MX is preferable to simply omitting MX records for a domain that intentionally does not accept mail because SMTP senders otherwise have an A/AAAA fallback defined by SMTP.

If you also publish an MTA-STS policy for a domain with a null MX, use `mode: none` and do not list any `mx:` entries. An enforcing or testing policy without an MX service would be inconsistent with the domain's intent.

If old DKIM selectors exist for the unused domain, remove them or publish revoked DKIM keys. For broad subdomain hardening, a wildcard revoked key can be used where appropriate:

```dns
*._domainkey.example.net.    TXT    "v=DKIM1; p=;"
```

Do not apply this configuration to a domain that is used by Postal or another service for legitimate mail. In particular, SPF does not inherit from the parent domain to child domains, while DMARC can inherit a parent policy when a subdomain does not publish its own policy. Review every sending subdomain before adding wildcard hardening.

::callout{icon="i-heroicons-exclamation-triangle" color="amber"}
`v=spf1 -all` is a hard fail and is appropriate for a domain that has no legitimate senders. Never use it on a domain that Postal or another legitimate sender will use.
::

## MX and inbound mail

MX is an independent architectural decision.

### Sending only

If another provider already receives mail for the sending domain, keep its existing MX records.

Postal can be used as an outbound sending platform without becoming the inbound mail server.

### Sending and receiving

If Postal should receive mail for the sending domain, publish an MX record pointing to one of the hostnames configured in `dns.mx_records`.

For a single-node installation:

```yaml
dns:
  mx_records:
    - postal.example.com
```

and:

```dns
example.com.    MX    10 postal.example.com.
```

For a multi-node installation, use the actual MX hostnames configured in `dns.mx_records`.

::callout{icon="i-heroicons-exclamation-triangle"}
Changing MX changes the inbound mail path. Do not replace an existing production MX record merely because Postal is configured for outbound delivery.
::

Postal's DNS checker reports a missing MX as `Missing`; however, if MX records exist and do not include all configured Postal MX hosts, the check may be reported as invalid. See the DNS configuration page for the relationship between `dns.mx_records` and Postal's checks.

## Sending subdomains

A sending subdomain is an independent Postal domain.

For example:

```text
transactional.example.com
```

may use:

```dns
transactional.example.com.    TXT    "postal-verification <TOKEN>"
transactional.example.com.    TXT    "v=spf1 include:spf.postal.example.com -all"
dkim-ABCDEF._domainkey.transactional.example.com.    TXT    "v=DKIM1; t=s; h=sha256; p=<PUBLIC_KEY>;"
psrp.transactional.example.com.    CNAME    rp.postal.example.com.
_dmarc.transactional.example.com.    TXT    "v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r; pct=100; rua=mailto:dmarc@example.com"
```

Every record is tied to the exact sending-domain namespace.

## DNS hierarchy rule

For a sending domain such as `example.com`, Postal expects:

```text
Verification:
    TXT on example.com

SPF:
    TXT on example.com

DKIM:
    <selector>._domainkey.example.com

Return Path:
    psrp.example.com

DMARC:
    _dmarc.example.com
```

For a sending subdomain such as `transactional.example.com`, the derived names move with that exact domain.

Do not move records to a parent domain because the shorter name looks cleaner.

## Production checklist

Before enabling production traffic for a sending domain, verify:

```text
[ ] The domain exists in the intended Organization or Mail Server.
[ ] Domain verification is successful.
[ ] SPF contains the configured Postal SPF include.
[ ] SPF uses -all in the final hardened policy.
[ ] The DKIM record exactly matches the record generated by Postal.
[ ] Postal reports the domain DKIM check as OK.
[ ] The Return Path CNAME resolves to the configured Return Path domain.
[ ] DMARC is published.
[ ] DMARC is eventually enforced with p=reject.
[ ] All legitimate sending sources are covered by SPF or DKIM.
[ ] Existing inbound MX has not been changed accidentally.
[ ] A real message has been tested and SPF, DKIM and DMARC results are as expected.
```
